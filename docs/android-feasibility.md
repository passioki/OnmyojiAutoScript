# Android 端运行可行性验证清单

> 目的：在**投入任何 OAS 代码改动之前**，用最少成本判定"OAS 跑在安卓手机上、
> 与阴阳师同机共存"这条路是否走得通。

---

# ★ 假设 A 已实测完成 —— **结论：通过**

**实测日期**：2026-10-08
**样本**：同一账号（`戀鳥樹`）的**庭院**界面，
手机 `2340×1080`（真机截图）vs 模拟器 `1280×720`（adb 截图）

## 结论

```
手机画面 = 模拟器画面 × 1.5 ，居中放置
    x_phone = 1.5 × x_emu + 210
    y_phone = 1.5 × y_emu
```

* **1.5** 恰好 = 高度比 `1080 / 720`
* **210** 恰好 = `(2340 − 1280×1.5) / 2 = 420 / 2`

即：**游戏把 16:9 画面等比放大居中，两侧各留 210px白边 —— 没有重排 UI。**

## 证据（三层，逐层加强）

### 层 1：全局模板匹配（48 个网格样本）

在整幅手机图里搜"从模拟器现取的 70px 块"的全局最优位置，**不限定任何预测**：

| 模型 | 样本 | 典型误差 | 最高相似度 |
|---|---|---|---|
| **M2 = `1.5x + 210`** | **35 / 48** | **0~1px** | **0.999** |
| M1 = `1.5x` | 5（含 2 个低分误匹配）| — | — |
| M3 = `1.5x + 420` | 8（**全在 x≥1050 的贴屏右边**，边界伪影）| — | — |

单点样本（误差几乎为 0）：

```
emu(   0, 330) → phone( 210, 495)   预测 210,495   相似度 0.995
emu( 900, 220) → phone(1560, 330)   预测 1560,330  相似度 0.987
emu( 150, 550) → phone( 435, 825)   预测 435,825   相似度 0.999
emu( 750, 110) → phone(1335, 165)   预测 1335,165  相似度 0.994
```

### 层 2：逐条带配准（最可靠）

把模拟器图按 1.5 放大成 `1920×60` 的**整行条带**，在手机图上滑动求最佳水平偏移：

```
模拟器 y → 最佳偏移
{0: 0, 60: 207, 120: 210, 180: 210, 240: 210, 300: 210,
 360: 210, 420: 210, 480: 210, 540: 210, 600: 210, 660: 210}
```

* **11 / 12 条带指到偏移 210**，`MAD` 仅 **0.06 ~ 0.38**（极低）
* 唯一例外 `y=0`（偏移 0）是**状态栏**——整行是纯色文字条，
  其 MAD 为 0.7076，比其他高一个量级，属匹配退化，非真实规律

★ 这一层用整行 1920×60 像素做**准全局**配准，比单模板匹配可靠得多。

### 层 3：OCR 交叉验证

两张图上 6 个 UI 文字的坐标，y 方向完美符合 `1.5×`（误差 ≤7px）。

## 对 OAS 的影响（好消息）

| 项 | 影响 |
|---|---|
| **1,935 条规则坐标** | ✅ **可通过一行公式换算**，不必重标 |
| **1,926 张模板图** | ⚠️ 需提**缩放**（尺寸也要 ×1.5）—— 但这是**纯机械操作**，可脚本批量做 |
| `tasks/` 49,002 行逻辑 | ✅ **完全不用改** |
| 坐标基准 1280×720 | ✅ 保持不变 —— 只要在设备层做"缩放 + 平移" |

**建议做法**：不改任何 `assets.py`，而是在**设备层**加一层坐标变换：

```python
# 截图时: 把手机画面裁剪 + 缩放到 1280x720
#   crop: (210, 0, 210 + 1920, 1080)   -> 1920x1080
#   resize: 1920x1080 -> 1280x720
# 点击时: x_emu, y_emu -> x_emu * 1.5 + 210, y_emu * 1.5
```

★ **这样 1,935 条规则、1,926 张模板图、49,002 行逻辑全都原样可用。**
游戏本身就是"放大居中"，所以裁剪+缩放是**无损还原**。

# 假设 B：免 root 能否稳定注入触摸

## 为什么关键

Android 的触摸注入有几条路，但**能点到别的 app 的路很窄**：

| 方式 | 能否点到**游戏** | 需要什么 |
|---|---|---|
| `Instrumentation.sendPointerSync` | ❌ 只能点自己 | — |
| `AccessibilityService` 手势 | ✅ | 无障碍权限 |
| 悬浮窗直接注入 `MotionEvent` | ⚠️ | **`INJECT_EVENTS` —— 普通 app 拿不到**（需 root 或系统签名）|
| 输入法（IME）| ❌ **只能往文本输入框写字** | — |

## ★ 关于"伪装成输入法"这个思路

**这条路不通** —— 输入法（`InputMethodService`）的 API 设计目标是
**向当前输入框提交文本**，它**没有**"点击屏幕上任意坐标"的能力。

能实现"悬浮窗 + 点任意位置"的，实际是 **`AccessibilityService` + 悬浮窗** 的组合
（悬浮窗负责显示，无障碍负责注入）。输入法外壳有时被用来**规避游戏的权限检测**，
但那不改变"真正干活的是无障碍服务"这个事实。

## 怎么测（30 分钟，需要一个 demo）

1. 写一个最小 Android app，申请 `AccessibilityService`
2. 实现"每 3 秒点击屏幕固定一点"
3. 在**阴阳师**上测试，观察：点击是否生效 / 延迟 / 游戏是否异常

## 通过判据

| 判据 | 阈值建议 |
|---|---|
| ✅ 点击稳定生效 | 成功率 > 95% |
| ✅ 延迟可接受 | **单次点击 < 300ms**（OAS 大量连点，慢了会超时）|
| ✅ 游戏无反制 | 连续跑 10 分钟无异常 |
| ❌ 延迟 > 1s 或频繁失效 | 这条路基本不可行 |

## 备选方案

| 方案 | 代价 |
|---|---|
| **root + `INJECT_EVENTS`** | 低延迟稳定，但要求 root（会砍掉大部分用户）|
| **无线 ADB 自连**（手机连自己）| ✅ **免 root** —— `adb tcpip` + 本机连接，**完全复用 OAS 现有 ADB 实现** |
| **Shizuku**（借 adb 权限给普通 app）| ✅ 免 root，社区常用；需用户手动授权一次 |

★ **"无线 ADB 自连"最值得优先考虑** —— 设备层已有的 `adb` 截图/点击实现可直接用
（`tasks/Script/config_device.py` 的 `serial` 默认 `"auto"`，支持任意 adb 目标）。

# 假设 C：免 root 能否稳定截图

| 方式 | 说明 |
|---|---|
| `MediaProjection` | ✅ 标准做法；⚠️ Android 14+ 每次会话需重新授权 |
| `AccessibilityService.takeScreenshot()` | ✅ API 30+ |
| ADB `screencap` | ✅（配合"自连"方案）|

## 风险

| 风险 | 说明 |
|---|---|
| **游戏可能禁止录屏** | 部分游戏在 `MediaProjection` 下黑屏 —— **必须实测** |
| 截图延迟 | `MediaProjection` 单帧可能 50~200ms |
| 授权摩擦 | Android 14+ 每次会话要重新确认，影响无人值守 |

## 通过判据

| 判据 | 说明 |
|---|---|
| ✅ 游戏画面正常可见 | 可继续 |
| ✅ 单帧 < 200ms | 勉强可用（OAS `screenshot_interval` 默认 0.3s）|
| ❌ 黑屏 / 被禁止 | 改用 ADB `screencap` |

# 假设 D：性能与发热

OAS 每帧要做几十次模板匹配 + OCR。实测（PC 端）规模：

| 项 | 数量 |
|---|---|
| `RuleImage` 规则 | **1,935 条** |
| 模板图片 | **1,926 张** |
| 模板尺寸 | 多数 40~75px |

## 影响

若单帧处理 > 1s，则 OAS 的 `screenshot_interval = 0.3s` 无法达到，
**战斗中**的响应可能跟不上。

## 缓解

| 办法 | 说明 |
|---|---|
| **决策留在 PC**（推荐）| 手机只截图/点击，识别与决策在 PC —— 见下方"方案 C" |
| NNAPI / GPU 委托 | ONNX Runtime Android 支持 |
| 降低识别频率 | 只在需要时识别 |

# 架构建议：**"手机做手眼，决策留 PC"**

```
┌───────────────── 手机 ─────────────────┐
│  OASX (Flutter, 已有 Android target)    │
│  ＋ 轻量原生插件：                        │
│      · MediaProjection / 无障碍截图      │
│      · AccessibilityService / ADB 注入   │
│      · 悬浮窗显示状态                    │
└────────────────┬───────────────────────┘
                 │ 截图 / 点击指令
                 ▼
┌──────── 任意机器（PC 或手机自身）────────┐
│  OAS 后端：识别 + 决策 + 调度             │
│  （49,002 行任务逻辑原样保留）            │
└────────────────────────────────────────┘
```

**优势**：零重写、复用已做的接口（`/schema` `/overview` `/run_control`）、
OASX 的 `android/` 目录已存在。
