### 3.3 ★★★ 周期任务 vs 临时任务：**能统一，而且差异只有 2 个"策略参数"**

> ★★ **用户提问（逐字）**：
> > "**L3的周期任务和临时任务在底层实现上是否能够统一架构来表达。
> >   这样每次创建新的任务只需要用一种架构就行。对L2也会有影响**"

#### ★★ 结论：**能统一，且应该统一** —— 它们**不是两种东西**，是**同一种"调度单元"的两组参数**

★ 实测：今天同一件事有 **4 条平行的实现**（★ 这才是"两套架构"的真相）：

| 关注点 | ★ 周期任务（`period != none`）| ★ 临时任务（`period == none`）|
|---|---|---|
| **完成记忆** | `task_state.record_success()`（`:189`）· `is_completed_in_period()`（`:219`）| `mark_entry_completed()`（`:994`）· `get_entry_completed()`（`:891`）|
| **过期方式** | ★ **按 period**（日/周/月）| ★ **按 session**（`completed_session == session_start`，`:885/887`）⇒ ★ 后端重启即过期 |
| **入队方式** | `auto_queue_of()`（`config.py:2579`）⇒ **自动补齐** | **手动**放进 `run_list` |
| **完成判据** | 跨周期累计 `target` | ★ **跑完即完成**（`entry_target_reached()`，`config.py:3997`）|

★★ **⇒ 差异全部落在 2 个维度上**：★ **① 什么时候"重新可跑"**（过期作用域）★ **② 谁把它放进队列**（入队策略）。
★ **不是"机制不同"，只是"参数不同"** ⇒ ★ **统一是可行的，成本主要在迁移，不在重新设计。**

#### ★★★ 统一模型：`TaskUnit`（调度单元）

```python
TaskUnit:
    task: str                              # 任务名
    # ── ① 过期策略（★ 用同一个字段表达周期/临时）
    expire: 'session' | 'daily' | 'weekly' | 'monthly' | 'never' | <timestamp>
    window: [start, end] | None            # 时间窗（已有 AvailabilityWindow）
    # ── ② 入队策略
    enqueue: 'auto' | 'manual'             # 周期=auto，临时=manual
    # ── ③ 额度（次数）
    quota: {source: counter|resource|none, target: int}
    # ── ④ 出口语义（★ 直接复用已落地但零采用的 module/flow）
    exit_map: Exit -> Outcome
```

★ **调度循环统一成一条**（★ 不再分两套 `get_next()`）：

```
候选 = 全部 TaskUnit（不分周期/临时）
  → 过滤① 时间窗          (window)
  → 过滤② 是否该跑        (expire: session/daily/weekly/never/timestamp)
  → 过滤③ 额度是否已满    (quota.target)
  → 排序                  (run_list 顺序 = 用户编排；后续可加资源/优先级)
  → 执行 → ★ 记账(统一 record) → ★ 出口(统一 Outcome)
```

★★ **关键发现（★ 这是本次审视最有价值的一条）**：
★ 统一需要的"**两级状态入口**"（周期任务 `entry_id=None`，必须按任务名存；临时按 `entry_id` 存）
★ **已经在 `task_state.py` 的 C10 里实现好了**（`get/set_state` + `get/set_entry_state` + `get/set_task_state`，
★ SPEC `§4.5-㉞` 记"✅ 已落地"，但 ★ **当前 0 采用**）
★ ⇒ ★★ **L3 的统一，正好就是 C10 的第一个真实用户** —— ★ 不用再造一套状态层。

#### ★★ 迁移路径（★ 分批，每批全量绿）

| 批 | 内容 | 工作量 | 风险 |
|---|---|---|---|
| **R1** | ★ 统一"**记账 + 过期**"：`record_success/is_completed_in_period` 与 `mark/get_entry_completed` ⇒ 收成 `record_outcome(unit, outcome)` + `is_due(unit)`；★ **旧函数保留为薄别名**（不破坏调用方）| **M** | ★ 中（两套键不同：task 名 vs entry_id ⇒ ★ 用 C10 两级键）<br>★★ **[10-15] R1-a 已落地**：新增 `module/config/schedule_unit.py`（`ScheduleUnit` + `expire` 映射 + **只委托、零行为变更**）+ 守卫 **23 条** + 注入验证真红（2 failed→还原 SHA 一致→23 passed）· ★ **R1-b 待做**：把方向翻过来（旧函数变薄别名）+ 切 `config.py`/`script.py` 调用点 |
| **R2** | ★ 统一"**候选生成**"：`get_next()`（`config.py:4350`）里两个分支收成一个循环，条件全走 `expire/quota` 参数 | **M** | ★ 中（这是调度核心）|
| **R3** | ★ `auto_queue` 从"推导"变"**显式字段**"（★ `enqueue`）| **S** | ★ 低 |
| **R4** | ★ `task_factory` / 前端只暴露**一个"调度单元"**概念（不再让用户选"周期/临时"）| **S~M** | ★ 低 |

★★ **R1+R2 做完，顺带解决 `L1-a 断点续跑`** —— 因为"重启就过期"变成 `expire` 的一个取值，
★ 而不是**内建的语义**（★ 现在临时任务的重启重打**是 session 过期策略的副作用**，不是独立 bug）。

#### ★★ 对 L2 的影响（★ 用户问到了点子上）

| 现在（两套） | 统一后（一套） |
|---|---|
| 建任务要决定"我是周期还是临时" | ★ **只填一个 `expire`**（`session` = 临时 · `daily/weekly` = 周期）|
| 周期/临时走不同记账、不同判据、不同前端显示 | ★ 一条 `TaskUnit` 声明；★ 前端只渲染一个概念 |
| `flow.json` 解释器要分别适配两类 | ★ **解释器只消费 `TaskUnit`**，与"周期/临时"无关 |
| ★ 用户要理解两种任务的心智模型 | ★ **只有一种** |

★ ⇒ ★★ **强烈建议：把 L3 的"统一架构"提到 L2 之前（或与 L2 并行）** ——
★ 否则 `flow.json` 解释器会**先按两套语义写一遍**，之后还要再统一一次（★ 白做两遍）。

## 6. ★★★ 我的建议（只要一句）

> ★★ **先做「减肝三小件」：L1-a 断点续跑 + L1-b `defer_until` + L4 不静默**（★ 都是 **S~M**）
> —— ★ 它们**不改架构**，★ 但立刻止住"白跑一夜 / 白花门票 / 不知道坏了"这三种**最气的肝**；
> ★★ **然后做 L3-0（周期/临时统一架构）** —— ★ 因为它是 **L2 的前置**（★ 否则 `flow.json` 要写两遍语义）；
> ★★ **再全力做 L2（从零新建任务 S1~S6）** —— ★ 这是**你自己能减肝**的那一件（能力交给你）；
> ★ 之后才是 **L3 周期重构** 与 **L1-c 资源账本**（大工程，需要在能验证的前提下做）。
