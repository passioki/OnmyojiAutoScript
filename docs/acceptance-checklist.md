## §1 快捷排序（两个**按钮**）+ **自由拖动**（用户 ③ 的核心 · ★ S7 后）

| # | 操作 | **期望** | ❌ 如果不对说明 |
|---|---|---|---|
| 1.1 | 进「任务列表」页, 看队列工具条 | 有「**定时排前面**」与「**固定排前面**」**两个按钮** | 若还有「调度优先级」**下拉** -> **旧版本没构建**（S7 已删）|
| 1.2 | 页面上**不该**再有 | ~~「优先级依据」下拉~~ · ~~「调度优先级」下拉~~ · ~~「⚠ 顺序要生效需选「列表优先」」提示~~ | T1 / S6 / S7 已逐步删掉 |
| 1.3 | 点「**定时排前面**」 | 队列**重排一次**: 定时类条目**全部挪到前面**, 固定类在后; ★ 同类之间**相对次序不变** | 没变化 -> `PUT /{script}/queue/sort` 没调通 |
| 1.4 | 点「**固定排前面**」 | 两类的先后**反过来**（同样稳定）| — |
| 1.5 | **再点一次同一个按钮** | ★ 顺序**不变**（**幂等** —— 它是一个"动作", 不是"开关"）| 若来回切换 -> 实现成了**模式**, 不是动作 |
| 1.6 | 点完排序后**刷新页面** | ★ 新顺序**保留**（因为它**写进了 `run_list`**）| 回退 -> 没写盘 |
| 1.7 | ★ 排序后**手动拖任意一条** | ★ **仍然自由** —— 「排前面」**不留状态**, 不会再把你拖的结果压回去 | 拖完又弹回 -> 残留了"模式"状态（S7 未彻底落地）|
| 1.8 | 点按钮时看**有没有**"选择已保存"之类的提示 | ★ **没有"模式"被记住**这回事; 按钮**不带选中态** | 有选中态 -> 界面仍按"三模式下拉"实现 |

### ★ 1.9 拖动约束: **已经没有约束了**（S7 的**最核心**验收点）

| 试什么 | **期望** |
|---|---|
| ★ 把一条**固定**任务拖到**定时**任务**上面**（跨类别）| ★ **成功**, 且**刷新后保持** |
| ★ 把一条**定时**任务拖到**固定**任务**上面**（跨类别）| ★ **成功**, 且**刷新后保持** |
| 同类内两条互相拖 | ★ **允许**（并**持久化** —— 刷新后还在）|
| 把「**休息**」条目往**上**拖（拖到任务中间）| ★ **接受**（**不弹错**）; ★ 但保存后它**仍在最后** —— 这是**归一化**, **不是拒绝** |
| 连续多次跨类别拖动 | ★ 每次都成功, 每次都持久化 |

★ **关键**: 若出现"**拖了 -> 界面动了 -> 闪回 + 弹出保存失败**", 那是
  "**前端放行、后端拒绝**"（判据不一致）。★ S7 已把**后端判据删掉**,
  理论上不该再出现; **若仍出现, 请记下拖的是哪两条**（那是一手证据）。

★ ★ **最容易复现的"假成功"**: "**能随便拖, 但没有任何提示**" ——
  那是前端**把后端的拒绝当成了成功**（历史 bug: 后端拒绝的返回体里
  **也带 `entries`**, 前端判"有 `entries` 就算成功"）。
  **验证方法**: 拖完 -> **刷新页面** -> 顺序**必须**是拖动后的样子。
  若回弹, 就是这一类问题。

## 出问题时请给我这些

| 项 | 为什么 |
|---|---|
| **点的是哪个排序按钮, 还是纯手动拖** | 用来区分"**排序动作**"（`PUT /queue/sort`）与"**拖动**"（`PUT /run_list`）两类问题 |
| **拖的是哪两条**（任务名 + 它们的类别）| 用来确认是不是**跨类别**拖动（S7 的核心场景）|
| **界面有没有闪回** | 有闪回 = 前端放行后端拒绝（判据不一致）|
| **拖动后刷新, 顺序是否保留** | 不保留 = 后端拒绝被前端当成成功了（★ S7 已删掉拒绝路径; 若仍出现说明有**残留判据**）|
| **进程 / 调度暂停的实际状态** | 运行控制条问题靠它区分"进程没跑"与"调度被暂停" |
