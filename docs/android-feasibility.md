# 背景：为什么这是个"换手眼"的问题

OAS 现在是「**外部控制**」：

```
PC ──adb──→ Android ──→ 阴阳师
   截图+注入点击
```

设想是「**同机共存**」：

```
手机
├── OAS 服务（原生进程 / 无障碍 / 悬浮窗）
│     直接截图、直接注入触摸
└── 阴阳师
```

**这不是"把 OAS 搬到手机上"，而是换掉它的手和眼。**

OAS 的实测规模（决定了改造难度）：

| 层 | 行数 / 数量 | 说明 |
|---|---|---|
| `tasks/` | **49,002 行** | 54 个任务的识别规则与流程 —— **价值都在这里** |
| `module/` | 25,993 行 | 图像识别 / OCR / 调度 |
| **规则数** | **1,935 条** `RuleImage` | 全部基于 1280×720 绝对坐标 |
| **模板图** | **1,926 张** | 同上 |

# A. 画面尺寸 —— ✅ **已实测通过**

## 结论

```
手机画面 = 模拟器画面 × 1.5 ，居中
    x_phone = 1.5 × x_emu + 210
    y_phone = 1.5 × y_emu
```

* **1.5** 恰好 = 高度比 `1080 / 720`
* **210** 恰好 = `(2340 − 1280×1.5) / 2 = 420 / 2`

即：**游戏把 16:9 画面等比放大居中，两侧各留 210px —— 没有重排 UI。**

**样本**：同一账号（`戀鳥樹`）的**庭院**界面，
手机 `2340×1080`（真机）vs 模拟器 `1280×720`（adb 截图）。

## 证据（三层，逐层加强）

### 层 1：全局模板匹配（48 个网格样本，不限定预测位置）

| 模型 | 样本 | 典型误差 | 最高相似度 |
|---|---|---|---|
| **`1.5x + 210`（居中）** | **35 / 48** | **0~1px** | **0.999** |
| `1.5x`（贴左） | 5（含 2 个低分误匹配）| — | — |
| `1.5x + 420`（贴右） | 8（**全在 x≥1050 的贴屏右边**，边界伪影）| — | — |

单点样本（误差几乎为 0）：

```
emu(   0, 330) → phone( 210, 495)   预测 210,495   相似度 0.995
emu( 900, 220) → phone(1560, 330)   预测 1560,330  相似度 0.987
emu( 150, 550) → phone( 435, 825)   预测 435,825   相似度 0.999
```

### 层 2：逐条带配准（最可靠）

把基准图按 1.5 放大成 `1920×60` 的**整行条带**，在手机图上滑动求最佳水平偏移：

```
模拟器 y → 最佳偏移
{0: 0, 60: 207, 120: 210, 180: 210, 240: 210, 300: 210,
 360: 210, 420: 210, 480: 210, 540: 210, 600: 210, 660: 210}
```

* **11 / 12 条带指到偏移 210**，`MAD` 仅 **0.06 ~ 0.38**（极低）
* 唯一例外 `y=0` 是**状态栏**（纯色文字条，MAD 0.71，匹配退化，非真实规律）

★ 这一层用整行 1920×60 像素做**准全局**配准，比单模板匹配可靠得多。

### 层 3：OCR 交叉验证

两张图上 6 个 UI 文字的 y 坐标完美符合 `1.5×`（误差 ≤7px）。

## 对 OAS 的影响（好消息）

| 项 | 影响 |
|---|---|
| 1,935 条规则坐标 | ✅ **可通过一行公式换算**，不必重标 |
| 1,926 张模板图 | ⚠️ 需缩放（纯机械操作，可脚本批量）|
| `tasks/` 49,002 行逻辑 | ✅ **完全不用改** |

**建议做法**：不改任何 `assets.py`，在**设备层**加一层坐标变换：

```
截图侧: crop(210, 0, 2130, 1080) -> 1920x1080 -> resize 到 1280x720
点击侧: x_phone = 1.5 * x_base + 210,  y_phone = 1.5 * y_base
```

★ **反向换算的顺序容易写错**：是"**先减偏移再除以缩放**"，即 `(x − 210) / 1.5`；
写成 `(x / 1.5) − 210` 是**错的**（差了 `210/1.5 = 140` 像素）。

## 复现方法

```bash
python dev_tools/diag_android_layout.py <手机截图> <模拟器截图>
```

两图必须拍**同一界面**（推荐庭院，且同一账号），否则结论无意义。

# B. 触摸注入 —— ⬜ 待测

## Android 允许哪些注入方式

| 方式 | 能否点到**别的 app** | 需要什么 |
|---|---|---|
| `Instrumentation.sendPointerSync` | ❌ 只能点自己 | — |
| `AccessibilityService` 手势 | ✅ | 无障碍权限 |
| 悬浮窗直接注入 `MotionEvent` | ⚠️ | **`INJECT_EVENTS`** —— 普通 app 拿不到（需 root 或系统签名）|
| 输入法（IME）| ❌ **只能往文本输入框写字** | — |
| **`adb shell input tap`** | ✅ | ADB 调试（免 root）|
| **root shell（`input` / 设备节点）** | ✅ | root |

## ★ 关于"伪装成输入法"（重要澄清）

**单靠输入法做不到点击。** `InputMethodService` 的 API 设计目标是
**向当前输入框提交文本**，它**没有**"点击屏幕上任意坐标"的能力。

能实现"悬浮窗 + 点任意位置"的，实际是 **`AccessibilityService` + 悬浮窗** 的组合
（悬浮窗负责显示，无障碍负责注入）。输入法外壳有时被用来**规避游戏的权限检测**，
但真正干活的是无障碍服务。

**实测印证**：分析大狮 APK 时确认它**同时**注册了输入法
（`BIND_INPUT_METHOD`）**和**具备注入能力（见附录），并非只靠输入法。

## 免 root 的替代方案

| 方案 | 说明 |
|---|---|
| **无线 ADB 自连** | 手机连自己（`adb connect 127.0.0.1:5555`）—— **完全复用 OAS 现有 ADB 实现** |
| **Shizuku** | 借 adb 权限给普通 app，社区常用；需用户手动授权一次 |

★ **"无线 ADB 自连"值得优先考虑**：OAS 的 `serial` 配置默认 `"auto"`，
**支持任意 adb 目标**，设备层一行都不用改。

## 待测项与判据

| # | 测什么 | 通过判据 |
|---|---|---|
| B1 | 免 root 下点击能否稳定生效 | 成功率 > 95% |
| B2 | 点击延迟 | **单次 < 300ms**（OAS 大量连点，慢了会超时）|
| B3 | root 下是否有更优路径 | 延迟 / 稳定性明显更好 |

# D. 性能 —— ⬜ 待测

OAS 每帧要做几十次模板匹配 + OCR。规模实测：**1,935 条规则 / 1,926 张模板图**。

## 影响

若单帧处理 > 1s，则 `screenshot_interval = 0.3s` 无法达到，
**战斗中**的响应可能跟不上。

## 待测项与判据

| # | 测什么 | 通过判据 |
|---|---|---|
| D1 | 手机上跑一次"截图 → 模板匹配 → 输出结果" | **< 300ms** |
| D2 | 手机上跑一次 OCR | **< 500ms** |

★ **D1 是决定性的**：如果一次匹配要 3 秒，整条路直接否决。

## 缓解办法

| 办法 | 说明 |
|---|---|
| **决策留在手机外** | 手机只截图/点击，识别与决策在别处 |
| NNAPI / GPU 委托 | ONNX Runtime Android 支持 |
| 降低识别频率 | 只在需要时识别 |

# E. 最硬的障碍：任务逻辑怎么上手机

**这才是真正的门槛** —— 不是截图和点击（那两个都能解决），
而是那 **49,002 行 Python 任务逻辑**。

## 三个方案

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 手机跑 Python** | Chaquopy（把 CPython 嵌进 APK）| +50~100MB，**慢**；opencv/onnxruntime 的 Android wheel 很难配齐 |
| **B. 移植到 Kotlin/Dart** | 重写执行层 | **等于重做项目** |
| **C. 只移植常用几个任务** | 手机上只实现 3~5 个任务 | 中（可控）|

## 为什么"移植"这么难

具体卡点：

| 卡点 | 说明 |
|---|---|
| **Python 运行时** | Android 上没有轻量可行的 CPython + OpenCV + ONNX 方案 |
| **49,002 行过程式代码** | 每个 `script_task.py` 200~1000 行，与 `BaseTask` API 深度耦合 |
| **iOS 完全不可能** | 平台不允许嵌入任意 Python 运行时 + 无法注入输入 |

## ★ 好消息：障碍 A（坐标）已解决，且知识层已有出口

| 已做的事 | 对移植的意义 |
|---|---|
| `module/config` 与设备层解耦（有架构护栏测试）| **调度层已平台无关**，可先行移植 |
| `tasks/<Name>/meta.py` 自描述 | 任务**元数据**可自动导出 → 别的语言能读 |
| `GET /schema` `GET /overview` | **前端/别的语言**不必读 Python 就能拿任务知识 |
| 坐标变换实测 | 1,935 条规则 + 1,926 张模板图**不用重做** |

★ 也就是说：**元数据层不用重写，只有执行逻辑需要重写。**

# 附：大狮 APK 逆向分析

**样本**：`大狮0802a-伪装输入法.apk`（28.7 MB / 1029 条目）
**方法**：静态分析（读取资产文件名与 DEX 字符串）—— **不是反编译后的代码**

## 身份

```
package      = com.app.wkinput        ("wkinput" = 伪装输入法)
versionName  = 6.1.1
manifest 含 BIND_INPUT_METHOD          ← 确实注册为输入法
组件含 com.ime.input.InputKb
权限 49 条，含 SYSTEM_ALERT_WINDOW / WRITE_SECURE_SETTINGS /
     INTERACT_ACROSS_USERS_FULL / REQUEST_INSTALL_PACKAGES
```

## ★ 真正的机制不是输入法/无障碍 —— 是 **zygote 注入**

| 资产 | 说明 |
|---|---|
| `assets/injectModifyCaptureMode/*/inject7`、`inject9` | **原生注入器**（ELF DYN，含 `ptrace`/`zygote`/`inject` 字符串）|
| `hookzygote.apk` | 被注入进 **zygote** 的 Java 载荷 |
| `libzygote.so` / `libyafa.so` | 注入配套 + yafa 虚拟空间（容器）|
| `libsubstrate.so` | **Cydia Substrate** hook 框架 |

`hookzygote` 的类名直接暴露了手法：

```java
Lcom/kaopu/tiantian/Hook_Application_attachBaseContext;       ← hook Application 启动
Lcom/kaopu/tiantian/Hook_ContextWrapper_attachBaseContext;
Ldalvik/system/DexClassLoader;                                ← 运行期动态加载 dex
Lcom/cyjh/myapplication/Main;                                 ← 注入后的载荷入口
android.view.WindowManager$LayoutParams                       ← 建悬浮窗
```

**通俗说**：用 ptrace 把自己注入 `zygote`（Android 所有 app 的"母体"），
于是**每个新启动的 app 里都有它的代码** —— 包括阴阳师。
这样它就在**游戏进程内部**，可任意截屏、任意注入触摸，**不受无障碍 API 的限制**。

## ABI 覆盖

```
x86             inject7, inject9, libyafa.so, libzygote.so, Inject
x86_64          inject7, inject9, libyafa.so, libzygote.so
armeabi-v7a     inject7,        libyafa.so, libzygote.so, Inject   ← ARM 32
arm64-v8a       inject7,        libyafa.so, libzygote.so, Inject   ← ARM 64
```

★ **ARM 版本存在** → 理论上支持真机。
（细节：`android≥9` 那套只有 x86/x86_64；`android<9` 那套四种架构齐全。）

## 截图与识别能力

| 库 | 作用 |
|---|---|
| `libsc*.so` / `libscVirtDisplay{19,21}.so` | 截图，**按 Android 版本分别适配**（VirtDisplay = VirtualDisplay/MediaProjection）|
| `libtinyCnn.so` + `assets/model/TinyCnnModel` | **自带 CNN 推理** |
| `liblept.so` + `libtess.so` | Tesseract/Leptonica **OCR** |
| `libzbarjni.so` | 条码识别 |

它**自带一整套图识别 + OCR**，不依赖外部。

# 鬼使黑归因：为什么"不能确定"是对的

当时使用大狮时，**四个独立因素同时暴露**：

| # | 嫌疑 | 当时暴露 | 能否用"换方案"消除 |
|---|---|---|---|
| 1 | **zygote/进程注入** | 有（要 root）| ✅ 能彻底消除 |
| 2 | **无障碍服务** | 有（用户确认开了）| ✅ 能（有替代方案）|
| 3 | **行为异常**（频率/路线/24h 不停）| 有 | ⚠️ 只能缓解 |
| 4 | **举报**（组队/结界突破时队友看到）| 可能 | ❌ 无法控制 |

**所以当时是"四项全中"，无法归因。** 这不是判断失误，是**变量太多**。

## 一个可以推理的点：注入 vs 无障碍

| | 进程注入 | 无障碍服务 |
|---|---|---|
| 在游戏进程**内部** | ✅ 游戏**看不到**外部来源 | ❌ 输入来自系统层 |
| 游戏能否检测 | 只能靠**行为特征** | 可**主动查询** `getEnabledAccessibilityServiceList()` |
| 额外风险面 | **要求 root**（root 本身是另一大风险面）| — |

★ **反直觉之处**：注入看起来更隐蔽，但它**要求 root**，而 root 本身会被检测。

## 因此：**无线 ADB 自连**是"可被主动查询的标记最少"的方案

| 维度 | 情况 |
|---|---|
| 需要 root | ❌ |
| 需要无障碍 | ❌ —— **游戏查不到** |
| 需要悬浮窗 | ❌ |
| 输入来源 | `input` 命令走 InputManager → evdev，与真实触摸**同一路径** |
| 游戏能查什么 | 只能查"USB/无线调试是否开启"（很多游戏不查，因为会误伤正常用户）|
| 复用现有代码 | ✅ OAS 现有 ADB 设备层**一行不用改** |

**代价**：每次点击起一个 shell 进程，约 **50~150ms**。
★ 可用**常驻 `minitouch`** 解决 —— OAS 已有 `module/device/method/minitouch.py`，
它是常驻进程，点击延迟 <10ms。

# 架构建议：**"手机做手眼，决策留 PC"**

```
┌───────────────── 手机 ─────────────────┐
│  OASX (Flutter, 已有 android target)    │
│  ＋ 轻量原生插件：                        │
│      · 截图（MediaProjection / screencap）│
│      · 注入（无障碍 / adb / root）        │
│      · 悬浮窗显示状态                    │
└────────────────┬───────────────────────┘
                 │ 截图 / 点击指令
                 ▼
┌──────── 任意机器（PC 或手机自身）────────┐
│  OAS 后端：识别 + 决策 + 调度             │
│  （49,002 行任务逻辑原样保留）            │
└────────────────────────────────────────┘
```

**优势**：零重写、复用已做的接口（`/schema` `/overview` `/run_control`）、
OASX 的 `android/` 目录已存在。
